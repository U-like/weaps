# DirectP2P LAB — экспериментальная матрица NAT (2026-10-30)

## Где находится эксперимент

Это отдельный эксперимент в репозитории `U-like/weaps`. **Не смешивать с Android-мессенджером `U-like/p2p_messenger`**: его исходники, ключи, история переписки, игровой движок и релизные ветки не изменялись.

- Исходная ветка: `direct-p2p-lab` (архив версии 0.2, Android CI).
- Эта ветка: `experiment/directp2p-nat-diagnostics` (зафиксированные выводы из тестов DirectP2P LAB 0.2).
- Полный код версии 0.2 (Android + Python + тесты) уже зафиксирован в GitHub-архиве `directp2p-project.tar.xz` из коммита `9d8e93c`. Успешная сборка Android: https://github.com/U-like/weaps/actions/runs/40917637753. Дополнительно создан переносимый локальный Git bundle со снимком всех исходников и результатов (`677f6d34f78d0c6ef8c737a40e87f21fd9397d79`).

## Проверенные комбинации

| Устройство/сеть 1 | Устройство/сеть 2 | Результат | Комментарий |
|---|---|---|---|
| ПК по LAN | Android по Wi-Fi того же роутера | DIRECT | Локальная сеть; ~16–19 мс RTT |
| ПК через домашний роутер | Android по мобильной сети оператора A | DIRECT_FAILED | UDP до STUN работает, peer-пакеты не подтверждены |
| Android по домашнему Wi-Fi | Android по мобильной сети оператора A | DIRECT_FAILED | Повторяется без Windows/ПК |
| Android по мобильной сети оператора A | Android по мобильной сети оператора B | DIRECT | Игровые пакеты в обе стороны; ~59–67 мс |
| Android по домашнему Wi-Fi | Android по мобильной сети оператора B | DIRECT | Через публичные IPv4; ~31–37 мс |

Операторы A и B разные. Действительные внешние IP/порты намеренно опущены: GitHub-репозиторий публичный.

## Достоверные выводы

1. Прямой UDP **через интернет** подтверждён на двух независимых мобильных сетях и на паре домашний Wi-Fi ↔ оператор B. Relay для игры в этих тестах не использовался.
2. Оператор A использует CGNAT и показывает разные внешние UDP-порты для разных публичных STUN-серверов; у оператора B отображение между этими двумя серверами стабильно. Это *признак*, но не полная классификация NAT.
3. В успешном тесте оператор A реально использовал для пакетов к партнёру **новый порт, не объявленный STUN**. Второй клиент принял этот peer-reflexive endpoint; меняющийся порт **не исключает DIRECT во всех сочетаниях**.
4. Домашний TP-Link Archer C50 V6 **не блокирует весь P2P**: с оператором B прямое соединение успешно. Оснований для factory reset нет.
5. Первые Android `EPERM` возникали после работы приложения в фоне; в контрольном прогоне при активном экране ошибки исчезли. Причинная связь с фоном пока не доказана.
6. В версии 0.2 ручная пересылка OFFER/ANSWER делает старт несимметричным. `direct_timeout` может возникнуть раньше `direct_established`. Получение нуля *аутентифицированных* пакетов не означает отсутствия любых сырых UDP-датаграмм.

## Диагностическая программа для версии 0.3

1. Двухфазный **READY/START** после обмена OFFER/ANSWER, общий таймер только после готовности обеих сторон.
2. Раздельные счётчики: raw UDP RX, packets accepted by HMAC, UDP TX attempts, sendto successes, sendto errors, причины и кандидаты.
3. Раздельно измерять NAT mapping и NAT filtering (RFC 5780-совместимая STUN-инфраструктура или контролируемые UDP-эндпоинты); не выводить NAT type по двум STUN адресам.
4. Peer-reflexive logging: действительный адрес/порт источника даже если не совпал с объявленным кандидатом.
5. IPv6 проверка и отдельная карта маршрутов; не смешивать её с IPv4 STUN.
6. Повторить сложную пару домашний Wi-Fi ↔ оператор A с обратными ролями при синхронном старте.
7. Только после этого сопоставлять инструментацию с iroh из `p2p_messenger`.

## Правило безопасности

В открытый репозиторий не коммитить полные JSON-отчёты, приватные IP, session keys, токены и данные переписки. Не проводить заводской сброс роутера ради эксперимента.
